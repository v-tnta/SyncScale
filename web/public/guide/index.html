はじめに

SyncScale プロジェクト概要

相対見積もり（S/M/L）を用いた、学生向けタスク管理能力・メタ認知支援ツール

解決する課題

学生が抱える「締切に追われる」心理的負担の根本原因は、自身の時間見積もり能力の甘さと着手の先延ばしにあります。従来のタスク管理ツールは「締切の管理」は支援しますが、「タスク規模ごとの着手の癖（先延ばし傾向）」を可視化する機能は存在しませんでした。

目的

学生が、タスク規模（S M L）ごとの着手リードタイム（締切の何日前に着手したか）と、タイマーログから自動生成される実績ガントチャートを通じて、自身の「時間の使い方の癖」を客観的に自覚（メタ認知）し、セルフマネジメント能力を向上させることを目指します。

アプローチ（4 ステップ）

Step手法担当プロダクト
1. 自動収集LMS（manaba 等）から課題・締切を自動取得Chrome 拡張機能
2. 相対見積もり課題に対して S/M/L をラベリングWeb モバイル
3. 計測と振り返りタイマーで実働時間を計測、完了時にコンディション入力Web モバイル
4. データの可視化着手リードタイム・実績ガントチャートを表示Web モバイル

新規性

相対見積もり（SML）× 先延ばし可視化

「完了/未完了」ではなく「タスク規模ごとに、いつ着手したか」に着目し、先延ばしの癖をメタ認知させます。

実績ガントチャートの自動生成

従来「未来の計画」のために高コストで作るガントチャートを、タイマーログから「過去の実績」として自動生成。計画立案の負荷なしに内省機会を提供します。

3 つの制作物

本プロジェクトは、3 つの制作物と共通ドキュメントで構成されたモノレポです。

プロダクト技術バージョン役割
Web アプリ React + Vite + Tailwind CSS 0.4.0 タスク管理・SML 見積もり・タイマー・分析・ガント・拡張機能との連携ハブ
Chrome 拡張機能 Manifest V3 + Vite 1.2.0 manaba から課題・締切を自動取得し、Web アプリ経由で Firestore へ登録
モバイルアプリ Flutter (Dart) 1.0.0 外出先での SML 評価・タイマー計測・コンディション入力・分析・締切前通知

3 つの制作物は Firebase（Firestore + Authentication）を Single Source of Truth として共有し、同一ユーザー・同一データでリアルタイムに連携します。

各プロダクトの役割

Web Web アプリ（React / Vite）

タスクの一覧管理・編集・削除、着手リードタイム分析、積み上げ式実績ガントチャート、〆切カレンダー、タイマー計測・手動記録、コンディション入力、研究利用同意・オンボーディング・チュートリアル、拡張機能とのハンドシェイク連携。

拡張 Chrome 拡張機能（MV3）

manaba の課題一覧ページから課題名・締切・科目をスクレイピング。chrome.storage.local を介した Storage ベースのイベント駆動連携（バケツリレー方式）。Firebase には直接接続しない設計。

モバイル モバイルアプリ（Flutter）

外出先での SML 評価・タイマー計測・コンディション入力・着手リードタイム分析・実績ガント・締切前通知。同一 Firestore を参照し Web とリアルタイム同期。

Firebase Firestore + Authentication

全プロダクト共有のデータストアと Google ログイン認証。セキュリティルールで「本人のみ・同意済みのみ」の読み書きを強制。

連携設計ポリシー

  • Firebase を Single Source of Truth とする。全プロダクトが同じコレクションを参照する。
  • Chrome 拡張機能は Firebase に直接接続しない。Web アプリの動作中タブを介したメッセージ連携のみで、拡張機能内に API キーや認証トークンを保持・露出させない。
  • 拡張機能と Web は chrome.storage.local と window.postMessage（ハンドシェイク）でやり取りするため、ページロードのタイミング差によるデータロストが起きにくい。
  • Web が未ログインの状態で拡張機能からデータを受信した場合、sessionStorage に一時保留してログイン誘導画面（/svc/ext-sync）を表示し、ログイン完了後に自動でインポートを実行する。
アーキテクチャ

データフロー

課題が manaba から取得されて分析に至るまでの、データの流れの全体像

① 課題インポートの流れ（拡張機能 → Web → Firestore）

拡張機能は Firebase に直接書き込みません。chrome.storage.local を共有バッファとして使い、各ページが自分でストレージを参照して次の動作を行う「バケツリレー方式」のイベント駆動連携を採用しています（chrome.tabs.sendMessage の直接通信は使いません）。

  1. 拡張Background（service worker）が manaba のタブを開く
    ユーザーがポップアップから同期を開始すると、manaba の課題一覧ページへ誘導します。
  2. 拡張content script が課題をスクレイピング
    content.js が課題名・締切・科目名・課題 URL（一意 ID）を抽出し、chrome.storage.local に保存します。
  3. WebWeb アプリが「準備完了」を宣言
    SyncScale の画面がマウントされると window.postMessage({ type: 'SYNC_SCALE_APP_READY' }) を発行します。
  4. 拡張web-content.js がタスクデータを送信
    READY を受けた web-content.js が chrome.storage.local のデータを SYNC_SCALE_IMPORT_TASKS メッセージで Web ページへ送ります。chrome.storage.onChanged により、開きっぱなしの SyncScale タブへもリアルタイムに再送されます。
  5. Web受信データを一時保存し ACK を返す
    受信データを sessionStorage.pendingImportTasks に保存し、SYNC_SCALE_IMPORT_ACK を返信します。拡張機能はこれを受けてストレージをクリアします（二重取り込み防止）。
  6. Web重複排除して Firestore に一括登録
    Firestore のタスク取得完了を待ってから、manabaAssignmentId（課題 URL）で既存タスクと突き合わせ、新規のみ writeBatch で一括登録します（isNew: true, source: 'chrome_ext'）。
  7. WebSML 見積もりモーダルで取捨選択
    取り込まれた課題には規模見積もりモーダル（TaskSizeEstimateModal）が連続表示され、課題ごとに S/M/L の評価、または「この課題は追加しない」を選べます。見送った課題は論理削除（isVisible: false）となり、manabaAssignmentId が残るため次回の同期で再インポートされません。

未ログイン時のフォールバック: Web が未ログインの状態でデータを受信した場合は sessionStorage に保留したまま /svc/ext-sync（ログイン誘導画面）を表示し、ログイン完了後に自動でインポートを再開します。

② タスクのライフサイクル

これからやる
→タイマー記録時に
startedAt をセット
DOING
とりかかり中
→提出完了時に
completedAt をセット
DONE
提出完了
  • タイマーの「きろく」時にステータスが TODO なら自動的に DOING へ更新し、startedAt が未設定なら計測開始時刻をセットします。事後の手動記録でも同様に補完します。
  • DONE への移行時にはコンディション（good / fair / poor）と振り返りメモの入力を促し、conditionLogs に記録します。
  • 「未提出に戻す」（DONE → TODO, completedAt = null）、論理削除（isVisible: false）・再表示・物理削除（関連ログのカスケード削除）が可能です。

③ 計測データの流れ（タイマー → 分析）

  1. Webモバイルタイマーで実働時間を計測
    取り組むタスクと（任意の）サブタスク名を選び Start/Stop。経過時間は「現在時刻 − 開始時刻」で毎秒再計算するため、PC のスリープでもズレません。事後の手動入力にも対応します。
  2. FirestoretimeLogs に保存
    開始・終了時刻と実働秒数（durationSeconds）を記録。これが実績ガントチャートの元データになります。
  3. Webモバイル分析画面で自動集計
    着手リードタイム（S/M/L 別の平均）、実績ガントチャート、カレンダーの作業実績インジケータ、サイズ別平均作業時間、よく作業する時間帯などに可視化されます（→ 分析機能）。

④ Web ⇔ モバイルのリアルタイム同期

Web アプリ・モバイルアプリはいずれも Firestore の同一コレクションを onSnapshot（リアルタイムリスナー）で購読しているため、片方での変更（タスク追加・SML 変更・タイマー記録など）はもう片方に即時反映されます。同期処理を独自に実装するのではなく、Firestore 自体を同期レイヤーとして利用しているのが特徴です。

Chrome 拡張機能（Manifest V3）

manaba から課題・締切を自動取得する収集レイヤー — Firebase には直接接続しない

構成

chrome-extension/src/
├── background/background.js   # service worker（タブ制御・オーケストレーション）
├── content/content.js         # manaba 用 content script（スクレイピング）
├── content/web-content.js     # SyncScale Web 用 content script（postMessage 連携）
├── popup/                     # ツールバーのポップアップ UI
└── options/                   # オプションページ

設計の要点

  • Storage ベースのイベント駆動連携: chrome.tabs.sendMessage による直接通信を使わず、各ページが自分で chrome.storage.local を参照して次の動作を行う「バケツリレー方式」。ページロードのタイミング差によるデータロストが起きにくい構造です。chrome.storage.onChanged で SyncScale タブへリアルタイム再送も行います。
  • Firebase へ直接接続しない: 拡張機能内に Firebase 資格情報や認証トークンを一切保持しません。Firestore への書き込みは、必ずログイン済みの Web アプリ（本人のブラウザセッション）を経由します。
  • 取得するのは課題名・締切・科目名・課題 URL（重複排除用の一意 ID）です。

外出先での SML 評価・タイマー計測・分析。Web と同一の Firestore をリアルタイム共有

構成

├── main.dart                     # 初期化（ネイティブのみ .env を dotenv.load）

│                                 # analytics.dart（着手リードタイム）/ onboarding.dart

├── widgets/                      # timer_panel / task_form_sheet / task_detail_sheet

│                                 # gantt_chart / manual_log_dialog / settings_dialog ...
├── services/                     # auth_service / syncscale_repository
└── state/syncscale_state.dart    # アプリ状態（タスク・ログの集約）

機能の要点

  • SML 入力: task_size_estimate_dialog.dart / task_form_sheet.dart で対応。Web と同じく sizeLabel を Firestore に保存します。
  • 着手リードタイム: analytics.dart の calculateLeadTimes は Web 版と同一定義（deadline − startedAt）です。
  • 締切前通知: タスクの締切前にローカル通知を配信（ネイティブアプリのみ）。設定値（notificationEnabled / notificationMinutesBefore）は userSettings/{uid} で Web と共有されます。通知の予約同期はキューで直列化され、削除済みタスクの通知が再登録されないよう制御しています（v0.4.0）。
  • 認証: auth_service.dart（Google ログイン）。
  • カレンダー: 月／週切り替え、週タイムグリッド（締切・作業ログの帯）、作業実績インジケータ。
  • チュートリアル: 動的チュートリアル 23 ステップ（通知機能の紹介を含む）。

Flutter Web ミラー（/svc/mobile/）

モバイルアプリは Web 向けにもビルドされ、React 版のホスティング配下（/svc/mobile/）に同梱されています。スマホ実機がなくてもブラウザからモバイル版の画面を体験できます。

  1. ルートで npm run build:mobile-web を実行すると、scripts/build-flutter-web.js が Flutter Web をビルドします（--base-href "/svc/mobile/"、Firebase キーは --dart-define で注入）。
  2. 成果物が web/public/svc/mobile/ にコピーされ、React 版のビルド・デプロイに同梱されます。

機能詳細

分析機能

「時間の使い方の癖」をメタ認知させる、本プロジェクトの中核機能

着手リードタイム分析（確定仕様）

定義: タスクごとに「最初に着手した日時（startedAt）が、締切（deadline）の何日前であったか」を算出します。

leadDays = (deadline − startedAt) / 86,400,000ms

正の値 = 締切前に着手（余裕日数）
負の値 = 締切後に着手（超過）
  • 集計: S M L それぞれについて、deadline と startedAt がともに存在するタスクの平均日数と件数を表示します。
  • 実装: Web = AnalyticsPanel.jsx#calculateLeadTimes、Flutter = analytics.dart#calculateLeadTimes。両者の定義は一致しています。
  • UI では平均日数に応じて「締切の N 日前／N 日後（超過）」と、簡単な気づきのアドバイスを表示します。

旧仕様の「登録日（createdAt）→ 着手日」の定義は採用していません。先延ばしの指標は「締切に対してどれだけ早く着手できたか」で評価します。

実績ガントチャート（GanttChart）

  • タスクの timeLogs を積み上げ式の水平スタックバーとして描画します。
  • 横軸 = 経過時間（0 分起点、30 分ごとの目盛り）。各ログ（サブタスク）を所要時間に応じた幅で左から隙間なく連結します。
  • バー内にサブタスク名を表示。コンテナ幅を超える場合は自動縮小、余裕がある場合は標準スケール（約 3px/分）。
  • 計画入力は不要で、タイマーログから「実績」を自動可視化します。

分析タブのその他のセクション

認証・セキュリティ

Google ログイン＋研究利用同意＋Firestore セキュリティルールによる防御

認証（Google ログインのみ）

  • Firebase Authentication の Google ログイン（signInWithPopup）のみを採用。匿名認証・アカウント連携は採用していません。
  • 認証状態は useAuth（AuthProvider）が onAuthStateChanged で監視します。

研究利用同意（Consent）

  • 本ツールは研究プロジェクトの一環であり、利用には研究利用への同意が必須です。consents/{uid} を onSnapshot で監視し、未ログイン → /login、ログイン済み・未同意 → /agreement へ誘導します（ConsentGuard）。
  • 同意の撤回時は全ユーザーデータ（tasks / timeLogs / conditionLogs / onboarding 等）を writeBatch で削除し、研究記録として withdrawnAt のみを記録します。

Firestore セキュリティルール

ルールは「本人のみアクセス可能」かつ「書き込みは同意済みユーザーのみ」を強制します。

コレクションreadcreate / updatedelete
tasks / timeLogs / conditionLogs所有者のみ所有者 かつ 同意済み所有者のみ
consents/{uid}本人のみcreate は agreedAt・version 必須。update は同意更新・撤回関連フィールドのみ不可
onboarding/{uid} / userSettings/{uid}本人のみ本人 かつ 同意済み本人のみ（撤回時の削除用）
activityLogs本人のみcreate のみ（追記専用・update 不可）本人のみ（撤回時の削除用）
  • isOwner(userId) = request.auth != null && request.auth.uid == userId
  • マッチしないパスは Firestore のデフォルトで deny されます。

Firebase 資格情報（API キー）の扱い

重要な前提として、Firebase のクライアント API キー・OAuth クライアント ID は「クライアントに配布される＝公開される」値であり、秘匿対象（シークレット）ではありません。これらを隠してもセキュリティは得られません。実効的な保護は次の 3 点で担保します。

  1. Firestore セキュリティルール — 不正な読み書きに対する実質的な防御線。
  2. API キー制限 — Firebase / Google Cloud コンソールで HTTP リファラ・アプリ・対象 API を制限。
  3. Authorized domains — 認証を許可するドメインの限定。
プロダクトキーの注入方法
Web アプリweb/.env（Git 管理外）の VITE_* をビルド時に埋め込み
Flutter（ネイティブ）mobile-app/.env（Git 管理外）を flutter_dotenv でアセットとして読み込み
Flutter（Web ビルド）scripts/build-flutter-web.js が --dart-define で埋め込み
Chrome 拡張機能キーを保持しない（Firebase に直接接続しない設計）

禁止事項: 真のシークレット（サーバー専用 API キー、第三者サービスの秘密鍵など）を Web バンドル・拡張機能・Flutter のクライアント資産に置かないこと。クライアント配布物では原理的に隠せません。.env / google-services.json 等は .gitignore で Git 追跡から除外しています。
