# SyncScale Web デザイン調査

調査日：2026-10-06。実装変更前の提案であり、確定仕様ではない。

## 結論

SyncScaleには、Atlassian Design Systemの情報整理・余白・文字階層を主軸にした、落ち着いた作業画面を推奨する。Material 3は色と状態の役割分け、デジタル庁は日本語の可読性の補助資料とする。複数の完成済みテーマを画面ごとに混在させるのではなく、参照した原則をSyncScale独自の一つのルールにまとめる。

これは公式資料と現在のコードからの設計判断であり、ユーザー調査によって実証した優劣ではない。今回の調査は公式Web資料・設計書・ソースコードの確認まで。ログイン後の実画面、実データ、ブラウザーでの表示、操作性、コントラストの実測は未確認。

## 1. 整ったウェブに共通する原則

| 原則 | 意味 | SyncScaleでの適用案 |
|---|---|---|
| 情報の階層 | 最初に見る内容、次に読む内容が分かる | 課題名と次の操作を主役にし、件数・補足・設定を弱める |
| 近接と整列 | 関係の近い情報は近づけ、異なるまとまりは離す | 課題名・締切・規模を同じ行のまとまりとして設計する |
| 余白の規則 | 任意の値を増やさず、限られた段階で組む | 4/8/12/16/24/32pxを初期候補とする |
| 色の役割 | 色名ではなく、何を伝える色かを決める | 主要操作・選択・規模・期限・作業実績を区別する |
| 文字の規則 | サイズ・太さ・行間を役割ごとに固定する | 画面見出し、セクション見出し、本文、補足の階層を作る |
| 面と奥行き | 背景・内容・一時的な重なりの関係を表す | 通常の領域は余白と境界、ダイアログ等には影を使う |
| 操作状態の一貫性 | 押せる、選択中、処理中、失敗を判断できる | hover・focus・disabled・loading・errorを共通化する |
| 内容に応じた密度 | 情報量と読みやすさの両方を保つ | 一覧は比較しやすく、見積もり入力や振り返りは余裕を持たせる |

余白・階層の根拠：[Atlassian Spacing](https://atlassian.design/foundations/spacing)、[Carbon Spacing](https://www.carbondesignsystem.com/building-blocks/foundations/spacing/overview)。文字の根拠：[Atlassian Typography](https://atlassian.design/foundations/typography)。色と面の根拠：[Material 3 Color roles](https://m3.material.io/styles/color/the-color-system)、[Atlassian Elevation](https://atlassian.design/foundations/elevation/)。具体的な適用案・数値は本調査の提案であり、すべてが各体系の指定値という意味ではない。

## 2. 候補の比較

| 体系 | 参照する内容 | SyncScaleへの評価・採用範囲 |
|---|---|---|
| Material 3 | 色の役割、文字の役割、状態を含む部品設計 | 有力候補。Webとモバイルで意味を共通化しやすい。PCで一覧を比較する用途に合わせ、余白や部品の大きさを検討する |
| Atlassian Design System | 余白、文字階層、境界・面の整理 | 主軸に推奨。タスク・締切・分析が共存する画面の判断材料になる。製品のブランドフォントや見た目をそのまま複製する必要はない |
| IBM Carbon | 情報の密度、グリッド、余白によるグループ分け | カレンダーや分析の補助参考。全体の外観を採用するかは学生向けの親しみやすさと合わせて判断する |
| Radix Themes / Primitives | Themesは外観の体系、Primitivesは動作の基盤 | 実装上の選択肢。現在のDialogはPrimitivesであり、Themesを導入済みという意味ではない |
| デジタル庁デザインシステム | 日本語書体・文字サイズ・行高の組み合わせ | 日本語の読みやすさの補助基準として推奨。行政サイトのレイアウト全体を採用する必要はない |

公式資料：[Material Typography](https://m3.material.io/styles/typography/applying-type)、[Atlassian Foundations](https://atlassian.design/foundations/)、[Carbon Spacing](https://www.carbondesignsystem.com/building-blocks/foundations/spacing/overview)、[Radix Themes](https://www.radix-ui.com/themes/docs/theme/overview)、[Radix Primitives](https://www.radix-ui.com/primitives/docs/overview/introduction)、[デジタル庁 Typography](https://design.digital.go.jp/dads/foundations/typography/)。Materialのページは直接取得ではJavaScript要求のみで、当該内容は検索で取得できた公式ページの記述を確認した。

「デザインシステムを採用する」と「UIライブラリを入れ替える」は別の判断になる。現状のReact・Tailwind・Radix Dialogを活用して共通ルールを実装できるため、調査時点では新規ライブラリの導入を前提にしない。

## 3. 現在のコードから見える違和感の候補

### 部分ごとの視覚表現に差がある

`web/src/components/Layout.jsx` のヘッダーボタンは `rounded-2xl`、`shadow-sm`、太めの文字とアイコンを使用。一方、`TaskForm.jsx` は外枠が `rounded-lg shadow-md`、登録ボタンは `rounded`。`Calendar.jsx` も `rounded-lg shadow-md`。`AnalyticsPanel.jsx` は `rounded-3xl`、多数の `font-black`、小さな補足文字を使う。

角丸の種類が複数あること自体は問題ではない。ただし「大きい面はこの角丸、通常操作はこの角丸」という説明可能な対応関係を決める余地がある。現状は部分ごとの強調が重なり、統一感を弱めている可能性がある。

### 補足の文字が小さい

`AnalyticsPanel.jsx` には9〜11pxの補足文字と薄いグレーの組み合わせがある。`index.css` のカレンダー時刻ラベルは11px、行高15px。限られた面積に収める意図は読み取れるが、振り返りに必要な情報まで弱くなっていないか、実画面で確認したい。コードだけではWCAG不適合とは断定しない。

### 登録・閲覧・作業の優先順位

`HomePage.jsx` は左カラムに登録フォーム、その後に一覧を配置し、`Layout.jsx` は右にカレンダーを置いている。登録フォームが上部を占有するため、日常利用で「取り組む課題を選ぶ」体験との優先順位を検討する余地がある。LMS取り込み中心なら折りたたみが有力だが、手入力が多い利用者には常時表示が適する可能性もある。

### レイアウトと情報密度

`Layout.jsx` の左右幅指定は45%と80%で、実際の幅はflexの縮小計算に依存する。直ちに不具合という意味ではないが、意図した比率・最小幅を明示すると調整しやすい。カレンダーは高さ660px固定で、24時間を圧縮して見せている。短い作業ログや狭い画面での読みやすさを確認したい。

### 色の意味が衝突する可能性

`index.css` ではLサイズが赤、Mサイズがオレンジ。規模の大小と、期限の危険度・エラーは別の意味なので、同じ警告色の印象が混ざる可能性がある。S/M/Lの文字を残し、規模色は低彩度化または警告と異なる配色を比較する。変更する場合はWeb・Flutter・拡張機能で意味を統一する。

### 活用できる既存の土台

`index.css` にブランド色・規模色・フォントのトークンがあり、`Modal.jsx` にはRadix Dialogによる共通の枠がある。これを拡張し、背景・文字・境界・角丸・影・操作状態まで共通化する方針が自然。

## 4. SyncScale向けの暫定デザインルール

目指す印象は「落ち着き、明瞭さ、少しの親しみやすさ」。設計書にある学生の見積もり・着手・内省の支援に合わせる。

- 背景は淡い中性色、内容は白を基本とする。青は主要操作と選択に用いる。
- 通常の領域は余白と細い境界で整理し、影は重なりを示す場面に絞る。
- 文字は既存のNoto Sans JPを継続候補にする。本文14〜16px、補足12〜13px、見出し18〜24pxを初期案とし、太さは400/500/700中心に整理する。日本語の長文説明は十分な行間を確保する。
- 角丸は入力・ボタン8px、領域12px、ダイアログ16pxを比較用の初期案とする。バッジは別扱いにする。
- 余白は4/8/12/16/24/32px中心。親のレイアウトと子の外側余白を重ねて二重に管理しない。
- 一つの操作領域では最も重要なアクションを明確にし、それ以外は控えめにする。計測中は停止操作を見失わせない。
- 課題行はタイトル・締切・規模・状態の順序と位置を揃える。色だけに意味を依存させない。
- 空状態・読込中・エラー・長い日本語タイトル・期限なしを通常のデザイン対象に含める。
- 振り返り画面は数値を比較しやすくし、規模が大きいこと自体を失敗のように表現しない。

以上はSyncScale向けの提案値で、公式体系への完全準拠を主張するものではない。

## 5. 品質の確認方法と次の進め方

1. 同じサンプル課題を使ってホーム画面の比較案を作る。推奨案はAtlassianの整理原則を基にした穏やかな外観。比較対象としてMaterial 3寄りの面・色使いの案を用意する。
2. 課題選択、S/M/L見積もり、計測開始・停止、振り返りへの移動で迷わないかを確認する。登録フォームの折りたたみは操作負荷も含めて判断する。
3. 方針決定後に、トークン、ボタン・入力・課題行・領域の共通部品、ホーム、分析画面の順に反映する。
4. 1280/1440pxのPC幅、狭い画面、200%ズーム、長い課題名、空状態、キーボード操作、フォーカス復帰を確認する。

アクセシビリティの確認基準にはWCAG 2.2 AAを用いる。通常文字のコントラストは4.5:1以上、大きな文字は3:1以上（適用対象・例外あり）。操作対象の最小寸法は原則24×24 CSS pxだが間隔等の例外がある。普段押すボタンは余裕を持った40〜44px程度を独自の設計目標として比較する。「WCAGでは全ボタン44px必須」という意味ではない。

根拠：[W3C Contrast Minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)、[W3C Target Size Minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)。これらの項目だけでWCAG全体への適合を保証するものではない。

この調査ではアプリのコード・依存関係を変更していない。提案を採用する場合に、正典の設計書との整合を取る。
